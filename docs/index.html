The Orim board format

An Orim board is a typed, structured graph that happens to have a spatial projection. This page specifies that graph: plain JSON, fully documented, designed to be read and written by things that aren't Orim.

Stability promise. Everything here is plain JSON and round-trippable. Changes within a schemaVersion are additive only; breaking changes bump the version and ship with documented migrations. Your data is never trapped: every board exports to this format in one click, and the format will always be openly documented.

The document

A board document has a schemaVersion, an id, a title, and three keyed collections: nodes, connectors, and comments — each a map from id to object. Ids are opaque strings, unique within their collection.

Common node fields

Every node shares a spatial and structural base. Coordinates are world units (unbounded, y grows downward); a sticky note is 180×120 by convention. index is a lexicographic z-order key — sort ascending, draw first-to-last. parent points at a frame and drives containment and reading order. data is a free-form bag of typed fields; this is what makes a board a database — votes, owners, SLAs, anything.

Node types

Connectors

Connectors are first-class edges, stored separately from nodes. An endpoint is either bound to a node ({ node, anchor } — the connector follows it) or a free point ({ point: {x, y} }). anchor is a side (n s e w) or auto, which picks the side facing the other end. Binding to a table may name a row; the connector then anchors to that row's edge and follows it — a link to a record, not a rectangle. Routing (elbows, obstacle avoidance) is presentation, not data: only endpoints are stored.

Comments

Threaded comments anchor to a node (following it) or a free point. Resolved threads keep their history but leave the canvas and exports.

Semantics

Reading order

One ordering drives the Markdown export, the accessibility tree, and agent reads: frames first (sorted spatially — rows top-to-bottom, left-to-right within a row band), each with its children spatially sorted, then loose nodes, then connectors. What you export is what a screen reader hears is what an agent reads.

Cell bindings

A node whose text derives from a table cell stores data.$source = { table, row, column }. The cell is the source of truth: editing the node writes through to the cell, and every bound node follows cell changes. Position stays entirely the node's own — the binding is data, not geometry.

Collaboration

Orim stores boards as Yjs documents (one CRDT map entry per object, one field per key, giving field-level last-writer-wins). This JSON format is the canonical snapshot of that document: exports serialize it, imports and agents write it, and any CRDT implementation that produces the same shape interoperates.

Interop

Every board exports as this JSON, a Markdown outline (tables become real Markdown tables, connectors a Connections list), Mermaid, SVG, and PNG. Markdown, Mermaid, CSV/TSV and Excel import back in. An MCP server exposes boards to AI agents: read_board, create_objects, update_objects, delete_objects, apply_layout, find_empty_space, synthesize_table.
